 # 设备接入与管理系统架构设计说明（优化版）

------

 # 一、背景与目标

 ## 1.1 架构目标

 本系统面向大规模 IoT 场景，核心目标：

 - 支持**百万级设备连接**
 - 支持**高并发数据上报（10万+/s）**
 - 支持**低延迟指令下发（<50ms）**
 - 支持**多协议扩展（MQTT / TCP / HTTP / 私有协议）**
 - 支持**统一设备模型**
 - 支持**水平扩展与高可用**

------

 # 二、总体架构设计

 ## 2.1 分层架构

 ```
 设备层
    ↓
 接入层（Go）
    ↓
 协议层（Go）
    ↓（gRPC 主链路）
 设备模型层（Java）
    ↓
 事件层（Kafka）
    ↓
 业务系统
 ```

------

 ## 2.2 核心设计原则（新增）

 1. **RPC 作为主链路（实时性）**
 2. **MQ 作为事件链路（解耦/异步）**
 3. **接入层无状态设计**
 4. **统一设备模型驱动业务**
 5. **分层解耦，协议与业务隔离**

------

 # 三、核心技术选型

 ## 3.1 接入层 & 协议层

 - 语言：Go
 - 网络模型：epoll + goroutine
 - 框架：
   - TCP：gnet / netpoll
   - MQTT：EMQX（可选）
 - 编解码：
   - Protobuf（主）
   - JSON（兼容）

------

 ## 3.2 服务通信

 - Go → Java：gRPC（主链路）
 - 序列化：Protobuf

------

 ## 3.3 消息队列

 - Kafka

 用途：

 - 事件流处理
 - 数据分析
 - 系统解耦

------

 ## 3.4 存储设计

 - Redis：设备实时状态
 - MySQL：设备元数据
 - TSDB（可选）：时序数据

------

 # 四、核心链路设计（重点）

------

 ## 4.1 上行主链路（实时）

 ```
 设备 → Go接入 → 协议解析 → 标准模型 → gRPC → Java
 ```

 特点：

 - 低延迟
 - 强一致处理
 - 支撑实时业务

------

 ## 4.2 上行事件链路（异步）

 ```
 Java → Kafka → 下游业务
 ```

 用途：

 - 数据分析
 - 流处理
 - 告警系统

------

 ## 4.3 下行链路（控制）

 ```
 业务系统 → Java → gRPC → Go → 设备
 ```

------

 ## 4.4 关键设计结论（必须明确）

 ❗ Kafka **不是主链路**

 | 类型     | 技术  | 作用      |
 | -------- | ----- | --------- |
 | 主链路   | gRPC  | 实时处理  |
 | 事件链路 | Kafka | 解耦/异步 |

------

 # 五、统一设备模型设计（重构版）

 ## 5.1 设计目标

 - 屏蔽协议差异
 - 统一数据结构
 - 支持多类型事件
 - 支持扩展与流处理
 - 支持原始数据追溯

------

 ## 5.2 设计思路

 统一采用：

  **DeviceEvent 作为唯一标准模型**

 避免：

 - 多层嵌套
 - 类型语义混乱
 - 扩展困难

------

 ## 5.3 模型定义

 ### 5.3.1 DeviceEvent

 ```
 class DeviceEvent {
     String eventId;
     String deviceId;
     EventType type;
     
     Map<String, Object data;
     
     long timestamp;
     long receivedAt;
     
     Metadata metadata;
     
     byte[] raw;
 }
 ```

------

 ### 5.3.2 EventType

 ```
 enum EventType {
     STATUS,
     EVENT,
     ALARM
 }
 ```

------

 ### 5.3.3 Metadata

 ```
 class Metadata {
     String protocol;
     
     String ip;
     int port;
     
     String topic;
     String productKey;
     
     Map<String, Object extensions;
 }
 ```

------

 ## 5.4 模型优势

 - 单一入口（降低复杂度）
 - 语义清晰（枚举化类型）
 - 易扩展（extensions）
 - 支持流处理（Kafka/Flink）
 - 可观测性增强（receivedAt）

------

 ## 5.5 示例

 # 十三、总结

 ## 核心架构原则

 1. Go负责连接与性能
 2. Java负责业务与模型
 3. Kafka负责异步与解耦
 4. gRPC负责实时链路

------

 ## 最终结论

 👉 **RPC是主链路，MQ不是主链路**
