

### 设备管理系统

#### 接入层

负责与设备通讯，完成与设备的交互。通过实现各种协议来适配设备。

该系统负责设备的接入管理。负责与设备通讯，完成与设备的交互。通过实现各种协议来适配设备。然后将设备的交互用消息的方式发送给MQ，后续的逻辑处理又另外的系统来完成。设计这个系统时有什么架构设计的推荐？

---

你这个系统本质上是一个**“设备接入网关（Device Access Gateway）+ 协议适配层 + 消息驱动架构”**。这种场景在物联网（IoT）、视频监控、工业设备接入里非常典型，设计好坏主要取决于：**扩展性、稳定性、解耦程度、吞吐能力**。

我结合你描述的特点（多协议、设备通信、MQ解耦、后端异步处理），给你一套**工程级架构设计建议（偏实战）**👇

------

# 一、整体架构分层（推荐模型）

建议拆成 5 层，而不是写成一个“大网关服务”：

```
                ┌──────────────┐
                │ 设备（TCP/UDP/HTTP/MQTT） │
                └──────┬───────┘
                       ↓
        ┌────────────────────────────┐
        │ ① 接入层（Connection Layer） │
        └──────────┬─────────────────┘
                   ↓
        ┌────────────────────────────┐
        │ ② 协议解析层（Protocol Layer）│
        └──────────┬─────────────────┘
                   ↓
        ┌────────────────────────────┐
        │ ③ 设备模型层（Device Model） │
        └──────────┬─────────────────┘
                   ↓
        ┌────────────────────────────┐
        │ ④ 消息转换层（Event Layer） │
        └──────────┬─────────────────┘
                   ↓
        ┌────────────────────────────┐
        │ ⑤ MQ（Kafka/RabbitMQ）     │
        └────────────────────────────┘
```

------

# 二、核心设计点（重点）

## 1️⃣ 接入层（高性能通信）

职责：

- 维护连接（TCP / UDP / WebSocket / MQTT）
- 心跳检测
- 连接状态管理

### 技术建议：

- TCP/UDP：Netty（必须）
- MQTT：EMQX / 自己桥接
- HTTP设备：Spring WebFlux（非阻塞）

### 关键点：

- **连接与业务完全解耦**
- 每个连接只做 IO，不做业务逻辑

👉 原则：

> 接入层 ≠ 业务层（避免写成“大泥球”）

------

## 2️⃣ 协议适配层（插件化设计 ⭐）

这是你系统的核心。

### 推荐模式：策略模式 + SPI 插件化

```
interface ProtocolHandler {
    boolean support(String protocol);
    DeviceMessage decode(ByteBuf buf);
    ByteBuf encode(DeviceCommand cmd);
}
```

### 每种协议独立实现：

```
protocol/
 ├── gb28181/
 ├── private_v1/
 ├── modbus/
 ├── mqtt/
```

### 注册方式：

- SPI（推荐）
- Spring 自动装配
- 配置中心动态加载（高级玩法）

👉 好处：

- 新设备接入 = 新增插件
- 不影响已有系统

------

## 3️⃣ 设备模型层（统一语义 ⭐⭐⭐）

这是很多系统做烂的地方。

### 问题：

不同设备协议数据格式完全不同：

```
设备A：{ temp: 36 }
设备B：{ t: 36, unit: "C" }
设备C：二进制...
```

### 解决：统一设备模型

```
class DeviceMessage {
    String deviceId;
    String type; // event / status / alarm
    Map<String, Object> properties;
    long timestamp;
}
```

```
class Metadata {
    String protocol;   // mqtt/tcp/http
    String ip;
    int port;
    String topic;
    String productKey;
}
```

```
class DeviceEvent {
    String eventId;
    DeviceMessage data;
    Metadata meta;
    byte[] raw; // 原始数据（可选） 
}
```

👉 核心思想：

> 协议差异 → 转换为统一“设备语义模型”

------

## 4️⃣ 消息层（MQ解耦 ⭐⭐⭐）

你已经做了，这是对的。

### 推荐模式：

```
Topic设计：
device.event.{type}
device.status
device.alarm
device.command.reply
```

### 关键点：

- **不要把原始协议数据直接丢MQ**
- 一定要是“标准化后的消息”

### MQ选型：

| MQ       | 优点     | 适合       |
| -------- | -------- | ---------- |
| Kafka    | 高吞吐   | 大规模设备 |
| RabbitMQ | 灵活路由 | 业务复杂   |
| Pulsar   | 云原生   | 大规模     |

------

## 5️⃣ 设备下行（命令通道）

很多人只做上行，忽略下行。

### 设计：

```
业务系统 → MQ → 接入系统 → 设备
```

### 关键点：

- 设备在线状态缓存（Redis）
- 连接映射表：

```
deviceId → channelId(Netty)
```

------

# 三、关键技术设计（工程级）

## 🔹 1. 会话管理（Session）

```
class DeviceSession {
    String deviceId;
    Channel channel;
    long lastHeartbeat;
}
```

存储：

- 本地缓存（Caffeine）
- 分布式（Redis）——多节点

------

## 🔹 2. 水平扩展（必须）

### 问题：

设备连接不能随便迁移

### 解决：

👉 一致性哈希 / 设备分片

```
deviceId % N → 网关节点
```

或：

- Nginx + hash
- 或 MQTT broker 分发

------

## 🔹 3. 背压 & 削峰

设备可能瞬间爆发数据：

### 方案：

- 内部队列（Disruptor / RingBuffer）
- 限流（RateLimiter）
- MQ缓冲

------

## 🔹 4. 高可靠（你之前提到“不能丢消息”）

必须做到：

### ✔ 本地落盘（可选）

- 写日志（WAL）

### ✔ MQ可靠投递

- confirm机制
- retry + dead letter

### ✔ 幂等设计

- messageId

------

## 🔹 5. 监控（必须）

建议指标：

- 在线设备数
- TPS
- 每协议流量
- MQ堆积
- 延迟

------

# 四、推荐架构升级（进阶）

## ⭐ 1. 事件驱动架构（EDA）

```
设备 → 事件 → MQ → 多系统消费
```

👉 解耦所有业务系统

------

## ⭐ 2. 规则引擎（可选）

用于：

- 告警
- 自动控制

例如：

```
温度 > 50 → 触发告警
```

------

## ⭐ 3. 数字孪生（高级）

维护设备状态：

```
设备影子（Device Shadow）
```

------

# 五、典型错误（你一定要避开）

❌ 把所有协议写在一个类
 ❌ 接入层直接写业务逻辑
 ❌ MQ里传原始二进制
 ❌ 没有设备统一模型
 ❌ 没有连接与设备绑定关系
 ❌ 单节点（无法扩展）

------

# 六、总结一句话架构

> **高性能接入（Netty） + 协议插件化 + 统一设备模型 + MQ解耦 + 分布式扩展**
