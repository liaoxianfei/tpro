需要在一个老程序里面增加设备参数告警的抑制功能，如何设计才能独立又公用？

-----------------------------------

在老程序（遗留系统）中增加新功能，最忌讳的就是“牵一发而动全身”。要想做到**独立**（不破坏原有核心逻辑）且**公用**（能够复用于不同设备和参数），最核心的设计思想是“非侵入式拦截”。

我们可以把告警产生的过程看作一条流水线。不要去动老程序“生成告警”的源头，而是在告警“准备输出（入库/推送）”的最后一公里进行拦截和过滤。

以下是为你设计的独立且公用的告警抑制方案：

## 核心设计方案：拦截器模式 + 规则引擎

我们可以设计一个**独立的告警抑制引擎（Suppression Engine）**。老程序只需要把生成的告警丢给这个引擎，由引擎决定是“放行”还是“拦截”。

### 1. 架构设计：怎么做到“独立”？

根据你老程序的耦合程度，可以选择以下两种接入方式：

- **轻度耦合（应用内拦截）：** 如果老程序有统一的告警发送接口（比如 `sendAlarm()` 或 `saveAlarm()`），利用装饰器模式（Decorator）或 **AOP（面向切面编程）**，在这个接口前插入一个“抑制过滤器”。
- **零耦合（旁路异步处理）：** 如果老程序的代码根本动不了，可以让老程序将告警发送到消息队列（MQ）或内部事件总线。由一个独立的“告警服务”去消费这些消息，并在服务内部实现抑制逻辑。

### 2. 数据模型：怎么做到“公用”？

要让所有设备和参数都能公用这套逻辑，必须把“抑制逻辑”抽象为**配置化的规则**，而不是写死在代码里。

你可以设计一张**告警抑制规则表（Alarm Suppression Rules）**：

| **字段名**        | **类型** | **说明**                                                     | **示例**                             |
| ----------------- | -------- | ------------------------------------------------------------ | ------------------------------------ |
| `rule_id`         | String   | 规则唯一ID                                                   | `RULE_001`                           |
| `scope_type`      | String   | 作用范围类型：GLOBAL(全局) / DEVICE_TYPE(设备类型) / DEVICE(单设备) / METRIC(特定指标) | `DEVICE`                             |
| `scope_value`     | String   | 对应范围的ID或标识                                           | `A_PHASE_TRANSFORMER_01`             |
| `alarm_code`      | String   | 告警类型/错误码（ALL表示所有）                               | `HIGH_TEMPERATURE`                   |
| `suppress_type`   | String   | 抑制类型：TIME(定时) / CONDITION(条件) / DEPENDENCY(关联) / FLAPPING(闪烁) | `TIME`                               |
| `suppress_params` | JSON     | 抑制的具体参数设置                                           | `{"start": "08:00", "end": "18:00"}` |
| `is_active`       | Boolean  | 规则是否启用                                                 | `true`                               |

### 3. 四种通用的抑制逻辑实现（公用核心）

抑制引擎内部通过“策略模式”实现以下几种常见的公用抑制行为：

- **定时抑制（Time-based）：**
  - *场景：* 某设备在每天凌晨2点到4点跑批维护，期间参数异常是正常的。
  - *逻辑：* 检查当前时间是否在规则配置的 JSON 时间段内，在则丢弃告警。
- **维护状态抑制（Condition-based）：**
  - *场景：* 设备正在被工程师线下检修。
  - *逻辑：* 引擎在收到告警时，先查一下 Redis 中该设备的状态。如果 `status == 'MAINTENANCE'`，直接拦截。
- **关联抑制/根因抑制（Dependency-based）：**
  - *场景：* 母线断电了，导致下面100个变压器全部报“通讯中断”。此时应该只报“母线断电”，抑制100个子告警。
  - *逻辑：* 配置父子拓扑关系。当收到子设备告警时，检查父设备在过去 X 分钟内是否触发了核心告警。
- **频繁闪烁抑制（Flapping-based）：**
  - *场景：* 某个温度在临界点上下波动，1分钟报了50次。
  - *逻辑：* 漏桶或令牌桶算法。在 Redis 中记录该设备+参数在过去 X 秒内的告警次数，超过阈值则进入抑制状态，直到恢复平静。

## 改造实施步骤

1. **抽离：** 在老程序中，找到告警最终落库（DB）或推送到前端（WebSocket/API）的那个类。

2. **注入：** 编写一个 `AlarmSuppressionManager`（抑制管理器），在落库/推送前调用它：

   Java

   ```
   // 伪代码示例
   public void handleAlarm(AlarmData alarm) {
       // 核心改动：只加这一行判断，完全不影响老程序的告警计算逻辑
       if (suppressionManager.isSuppressed(alarm)) {
           log.info("告警被抑制: {}", alarm.getId());
           return; // 被抑制，直接返回，不落库、不通知
       }
   
       // 老程序的原有逻辑
       oldSaveToDatabase(alarm);
       oldPushToClient(alarm);
   }
   ```

3. **缓存提速：** 因为告警判断是高频操作，把规则表和设备状态加载到 **Redis** 中。每次告警来时，直接在内存中匹配规则，耗时控制在几毫秒内，保证不会拖慢老程序的性能。

这种设计的优势在于，未来无论增加什么新设备、新参数，或者要求调整抑制时间，你都**不需要再改动任何一行代码**，只需要在数据库里增加一条规则配置即可。

## 独立告警处理程序（补充完整）

将抑制引擎从老程序中进一步抽离为**独立告警服务**后，数据输入与处理建议如下。

### 数据输入端

| 入口 | 说明 | 适用场景 |
| --- | --- | --- |
| **Kafka / MQ 消息** | 消费上游产生的告警或设备事件 Topic（设备平台统一为 Kafka，见 `documents/devicemanage/01-架构设计基线.md`） | 主路径；与接入平台解耦 |
| **HTTP 接口** | 提供 `POST /alarm/ingest` 之类接口，供无法改造成发 MQ 的老系统推送 | 过渡期兼容 |
| **Prometheus / Alertmanager（可选）** | 接收 Alertmanager Webhook，将监控告警纳入同一抑制与通知管道 | 基础设施告警与业务告警统一运营 |

### 处理管道（建议）

```
输入（Kafka / HTTP / Webhook）
  → 规范化 AlarmData
  → AlarmSuppressionManager（定时 / 维护 / 关联 / 闪烁）
  → 放行：落库 + 通知（邮件 / 短信 / IM / WebSocket）
  → 拦截：记抑制日志（可采样），不打扰值班
```

### 与设备接入平台规则引擎的边界

| 能力 | 归属 |
| --- | --- |
| 设备接入后的实时阈值、协议侧告警初判 | `kingtype-device` / 设备域规则 |
| 对「已生成告警」做抑制、降噪、根因合并 | **本独立告警抑制服务** |

二者可共用「规则配置化」思想，但**进程与代码库分离**，避免把遗留抑制逻辑塞进 Go 接入层。

### 输出端

- 告警存储（MySQL / ES）
- 通知渠道
- 可选再投递 Kafka（如 `alarm.notified`）供报表与审计

### 实施注意

- 规则与设备维护状态优先缓存 Redis，保证高频判断延迟。
- 输入需幂等（alarmId / fingerprint），防止 MQ 重复投递导致重复通知。
- 独立服务同样纳入多租户：`tenant_id` 随告警载荷传入并做隔离。
